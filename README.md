# Saby CRM — Playwright-автотесты

Playwright + TypeScript. Проверяют карточку физического лица, карточку темы
«Лид» и реестры «Контактные лица» и «Темы» на тестовом стенде Saby:
визуальные эталоны, функциональные сценарии, а также создание и редактирование
временных ФЛ и темы.

## Структура

```
tests/
  support/
    constants.ts     # URL, настройки темы и параметры доступа
    auth.ts          # вход через SSO
    global-setup.ts  # однократная авторизация, сохранение storageState
    ui.ts            # хелперы: реестры/темы/карточки, создание, заполнение, удаление
    theme-dynamic.css # скрытие динамических данных на скриншотах темы
  test-1.spec.ts     # визуальные проверки карточки ФЛ
  test-2.spec.ts     # визуальные проверки карточки темы
  test-3.spec.ts     # smoke-проверка страницы входа
  test-4.spec.ts     # функциональные проверки карточки ФЛ
  test-5.spec.ts     # функциональные проверки карточки темы
  test-6.spec.ts     # открытие карточки ФЛ по ссылке в новой вкладке
  test-7.spec.ts     # реестр «Контактные лица»: поиск и фильтры
  test-8.spec.ts     # реестр «Темы» и окна счётчиков
  test-9.spec.ts     # создание/заполнение ФЛ и редактирование полной карточки
  test-10.spec.ts    # новая тема: изменение этапа «Новый»
  test-11.spec.ts    # пустой пользователь: заглушка, ФЛ, контактное лицо, папка, тег, выборка
  test-12.spec.ts    # документы продаж: создание, фильтр, поиск, редактирование
  test-13.spec.ts    # копирование темы «Проверка СПК» и проверка кода/форм/параметров
  *-snapshots/       # эталонные скриншоты
playwright.config.ts
COVERAGE.md          # матрица покрытия и непокрытые области
```

## Запуск

```bash
npm ci
npx playwright install chromium
npm test
```

Для запуска нужен доступ к тестовому стенду. Параметры доступа передаются
через переменные окружения или секреты CI и не публикуются в README.
Имена переменных и настройки CI — в `.github/workflows/playwright.yml`.

Перед тестами `global-setup` один раз выполняет вход и сохраняет сессию в
`playwright/.auth/user.json`. Все тесты стартуют уже авторизованными, поэтому
вход не повторяется в каждом тесте.

Полезные команды:

```bash
npm run test:headed     # с открытым браузером
npm run test:ui         # интерактивный режим
npm run test:update     # пересоздать все эталонные скриншоты
npm run report          # открыть HTML-отчёт
npx playwright test tests/test-11.spec.ts  # только сценарии пустого пользователя
```

## CI (GitHub Actions)

В `.github/workflows/playwright.yml` два независимых job'а на `windows-latest`:

- **основной набор** — установка зависимостей, Chromium и все тесты, кроме
  сценариев с тегом `@empty-user` (`--grep-invert "@empty-user"`);
- **пустой пользователь** — сценарии с тегом `@empty-user` (сейчас это
  `tests/test-11.spec.ts`): заглушка, физическое лицо, контактное лицо,
  папка, тег и выборка.

Job'ы изолированы друг от друга и могут выполняться параллельно.
Имена проверок в GitHub: `Playwright (Windows)` и
`Playwright — пустой пользователь (Windows)`.
Каждый job публикует свои артефакты:

- `playwright-report` / `test-results` — основной набор;
- `playwright-report-empty` / `test-results-empty` — сценарии пустого пользователя.

При падении в лог job'а дополнительно печатается `error-context.md` (снимок
страницы и ошибка), список файлов `test-results` и пути screenshot/trace.
В CI включён `github` reporter, поэтому ошибки также попадают в аннотации
GitHub Actions. Хелперы пишут в лог этапы авторизации, URL после навигации и
скопированную ссылку — по этим строкам видно, на каком шаге упал тест.

Секреты для доступа к тестовому стенду задаются в настройках репозитория.
Их имена и значения не публикуются в README; необходимый набор описан в
`.github/workflows/playwright.yml`. Job пустого пользователя запускает полный
Chromium: headless-shell не проходит проверку отпечатка устройства в SSO Saby.
Если стенд Saby доступен только из корпоративной сети, замените
`runs-on: windows-latest` на метку self-hosted Windows-раннера в обоих job'ах.

## Доступ к стенду и тестовые данные

Параметры доступа к тестовому стенду передаются через переменные окружения
или секреты CI. Конкретные значения не публикуются в README. Имена переменных
и настройки CI — в `.github/workflows/playwright.yml`.

Для темы можно переопределить параметры:

| Переменная | По умолчанию |
|---|---|
| `SABY_THEME_UUID` | `01a03962-b5ad-787c-a0f4-e78c18ca888a` |
| `SABY_THEME_TYPE` | `Лид` |

Сценарии с пустым тестовым профилем используют отдельную сессию:
`global-setup` сохраняет её в `playwright/.auth/empty44.json`. Вход выполняется
в полном Chromium (`channel: 'chromium'`): headless-shell не проходит проверку
отпечатка устройства в SSO Saby.

## Скриншоты

- Эталоны сняты для **Chromium / Windows**. Для другого браузера или ОС нужны
  отдельные baseline-файлы, поэтому в конфиге оставлен только Chromium.
- Динамические данные (счётчик сделок, номера этапов, проценты, фильтр) скрываются
  через CSS перед снимком карточки темы. Это сохраняет геометрию страницы и убирает
  ложные падения из-за изменения данных.
- В карточке ФЛ маскируется возраст (зависит от текущей даты), в визитке — сумма
  в блоке продаж.
- При осознанном изменении интерфейса обновляйте эталон:
  `npm run test:update`, затем просмотрите diff в HTML-отчёте.

## Что проверяется

- `test-1`: визуальные проверки — пустая мини-карточка ФЛ; полная карточка
  (Параметры, Покупки, Активности); заполненная карточка; визитка из списка
  договоров.
- `test-2`: визуальные проверки 11 разделов карточки темы «Лид».
- `test-3`: доступность страницы входа Saby.
- `test-4`: функциональные проверки карточки ФЛ — структура мини-карточки,
  закрытие без сохранения, последовательное переключение вкладок, данные
  заполненного клиента и визитки.
- `test-5`: функциональные проверки темы — полнота меню, содержимое воронки,
  параметры, роли, ссылки верхней навигации и последовательный обход разделов.
- `test-6`: открытие карточки ФЛ по ссылке, скопированной из живой карточки,
  в новой вкладке; отдельно проверяется команда «В новой вкладке». Кнопка
  «Ссылка/Поделиться» в актуальной версии Saby копирует ссылку сразу, а команда
  «В новой вкладке» находится в подменю этой кнопки в меню карточки. Ссылка
  читается из буфера обмена, а не задаётся в тесте.
- `test-7`: реестр «Контактные лица» — активный раздел, список с телефонами и
  email, поиск по фамилии, фильтры по полу и возрасту.
- `test-8`: реестр «Темы» — группы, строки тем и папок, колонки счётчиков,
  переход в карточку темы и три окна счётчиков строки «Тема для статистики»
  («Просроченные», «В работе», «Новый, Новые») с проверкой списка сделок и
  закрытия.
- `test-9`: два сценария с временной ФЛ — заполнение мини-карточки (ФИО, телефон,
  примечание, дата рождения, пол, адрес, паспорт, место рождения) с проверкой
  в полной карточке и изменением примечания; создание ФЛ с переходом в полную
  карточку, заполнением основных полей, сохранением и повторным открытием.
- `test-10`: создание временной темы «Продажи», проверка этапа «Новый», открытие
  карточки этапа, изменение его названия, сохранение темы, повторное открытие
  и удаление.
- `test-11`: пустой тестовый профиль — скриншот заглушки и проверка её
  положения; создание и удаление по отдельности физического лица, контактного
  лица (с временной организацией), папки, тега и выборки с фильтром
  «Пол» = «Мужской». Каждый тест завершается проверкой, что страница снова
  показывает исходную заглушку.
- `test-12`: документы продаж в карточке ФЛ — создание «Счёта», «Заказа от
  покупателя», «Реализации» и «Коммерческого предложения», сохранение
  комментария, отображение в списке и фильтре, фильтрация по типу, поиск по
  комментарию, редактирование сохранённого документа и удаление счёта с
  проверкой исчезновения его типа из фильтра.
- `test-13`: копирование темы «Проверка СПК» — код этапа «Код при копировании»,
  итог «Итоги пользователя», формула видимости перехода, формы, параметры и
  доп. поля копии; изменение кода формулы в копии с проверкой неизменности
  оригинала и уникального UUID.

Сценарии `test-1` — `test-8` только читают данные. `test-9` — `test-13` создают
временные записи с уникальными именами и удаляют их после проверки; `afterEach`
удаляет запись и при падении теста, чтобы не засорять общий стенд.
Матрица покрытия и список непокрытых областей — в `COVERAGE.md`.
