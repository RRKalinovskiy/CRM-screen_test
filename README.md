# Saby CRM — Playwright-автотесты

Playwright + TypeScript. Проверяют карточку физического лица, новую карточку
ФЛ под фичей `crm_new_individual`, карточку темы «Лид», реестры «Контактные
лица» и «Темы» и импорт ФЛ из Excel на тестовом стенде Saby: визуальные
эталоны, функциональные сценарии, а также создание, редактирование и импорт
временных ФЛ.

> Это копия suite для стенда `test` (ветка `test-stand`, `https://test-online.sbis.ru`,
> вход через `test-sso.saby.ru`). Отличия от `main`, статус адаптации,
> пропущенные проверки и ограничения CI — в `TEST-STAND.md`.

## Запуск

```bash
npm ci
npx playwright install chromium
npm test
```

Для запуска нужен доступ к тестовому стенду. Параметры доступа передаются
через переменные окружения или секреты CI и не публикуются в README.
Имена переменных и настройки CI — в `.github/workflows/playwright.yml`.

Перед тестами `global-setup` один раз выполняет вход и сохраняет сессию в
`playwright/.auth/user.json`. Все тесты стартуют уже авторизованными, поэтому
вход не повторяется в каждом тесте.

Полезные команды:

```bash
npm run test:headed     # с открытым браузером
npm run test:ui         # интерактивный режим
npm run test:update     # пересоздать все эталонные скриншоты
npm run report          # открыть HTML-отчёт
npx playwright test tests/test-11.spec.ts  # пустой пользователь (на test недоступно)
npx playwright test tests/test-14.spec.ts  # только новая карточка ФЛ
npx playwright test tests/test-15.spec.ts  # карточка темы из реестра сделок
npx playwright test tests/test-16.spec.ts  # карточка темы по ссылке в отдельном окне
npx playwright test tests/test-17.spec.ts  # импорт ФЛ из Excel
```

На стенде test профиля `Пустой44` нет, поэтому основной прогон выполняется без
сценариев пустого пользователя:

```bash
npx playwright test --grep-invert "@empty-user"
```

## CI (GitHub Actions)

В копии для test-stand workflow запускается только вручную (`workflow_dispatch`)
и требует доступа к корпоративной сети/VPN; job пустого пользователя отключён.
Подробности — в `TEST-STAND.md`. Ниже описана схема основного репозитория.

В `.github/workflows/playwright.yml` два независимых job'а на `windows-latest`:

- **основной набор** — установка зависимостей, Chromium и все тесты, кроме
  сценариев с тегом `@empty-user`. В него входят сценарии `@new-card`
  (`tests/test-14.spec.ts`) в основной сессии: фича `crm_new_individual`
  включена для всех, сценарии `@theme-card` из `test-15`/`test-16` и импорт
  ФЛ из Excel (`@import`, `test-17.spec.ts`);
- **пустой пользователь** — сценарии с тегом `@empty-user` (сейчас это
  `tests/test-11.spec.ts`): заглушка, физическое лицо, контактное лицо,
  папка, тег и выборка.

Job'ы изолированы друг от друга и могут выполняться параллельно.
Имена проверок в GitHub: `Playwright (Windows)` и
`Playwright — пустой пользователь (Windows)`.
Каждый job публикует свои артефакты:

- `playwright-report` / `test-results` — основной набор, включая новую карточку ФЛ;
- `playwright-report-empty` / `test-results-empty` — сценарии пустого пользователя.

При падении в лог job'а дополнительно печатается читаемая сводка
`test-results/failure-summary.md`: для каждого упавшего теста — название,
файл и строка, номер попытки, причина, последние логи теста и пути
screenshot/trace. Эта же сводка добавляется в `GITHUB_STEP_SUMMARY`,
поэтому причины видны на странице запуска GitHub Actions без скачивания
артефактов. После сводки печатается `error-context.md` (снимок страницы и
ошибка) и список файлов `test-results`. В CI включён `github` reporter,
поэтому ошибки также попадают в аннотации GitHub Actions. Хелперы пишут в лог
этапы авторизации, URL после навигации и скопированную ссылку — по этим
строкам видно, на каком шаге упал тест.

Секреты для доступа к тестовому стенду задаются в настройках репозитория.
Их имена и значения не публикуются в README; необходимый набор описан в
`.github/workflows/playwright.yml`. Основной job и job пустого пользователя
запускают полный Chromium: headless-shell не проходит проверку отпечатка
устройства в SSO Saby. Если стенд Saby доступен только из корпоративной сети,
замените `runs-on: windows-latest` на метку self-hosted Windows-раннера в обоих
job'ах.

## Доступ к стенду и тестовые данные

Параметры доступа к тестовому стенду передаются через переменные окружения
или секреты CI. Конкретные значения не публикуются в README. Имена переменных
и настройки CI — в `.github/workflows/playwright.yml`.

Для темы можно переопределить параметры:

| Переменная | По умолчанию |
|---|---|
| `SABY_THEME_UUID` | `5440011c-8d41-11e7-adf1-005056b7473e` |
| `SABY_THEME_TYPE` | `Лид` |

Сценарии с пустым тестовым профилем используют отдельную сессию:
`global-setup` сохраняет её в `playwright/.auth/empty44.json`. Вход выполняется
в полном Chromium (`channel: 'chromium'`): headless-shell не проходит проверку
отпечатка устройства в SSO Saby.

Сценарии новой карточки ФЛ используют основную сессию: фича
`crm_new_individual` включена для всех пользователей, отдельный профиль
не нужен. Хелперы работают с новой разметкой `.crm_IndividualCardNew` и
сохраняют fallback на старую `.crm_IndividualCard`: кнопки редактирования и
сохранения ищутся по `data-qa="crm_IndividualCard__edit"` и
`crm_IndividualCard__saveButton`, дата рождения — по
`pd-componentsBirthDateInput`, пол — по `pd-componentsGender`, вкладки — по
`[name="tabparams"]` внутри корня карточки. Контакты в новой карточке
редактируются отдельным контролом.

## Скриншоты

- Эталоны сняты для **Chromium / Windows**. Для другого браузера или ОС нужны
  отдельные baseline-файлы, поэтому в конфиге оставлен только Chromium.
- В ветке `test-stand` эталоны `test-1` и `test-2` пересняты на стенде test:
  карточка ФЛ снимается в режиме «Колонки», тема — «Продажа товаров и услуг».
  Baseline из `main` для test не подходят.
- Динамические данные (счётчик сделок, номера этапов, проценты, фильтр) скрываются
  через CSS перед снимком карточки темы. Это сохраняет геометрию страницы и убирает
  ложные падения из-за изменения данных.
- В карточке ФЛ маскируется возраст (зависит от текущей даты), в визитке — сумма
  в блоке продаж.
- При осознанном изменении интерфейса обновляйте эталон:
  `npm run test:update`, затем просмотрите diff в HTML-отчёте.

## Что проверяется

- `test-1`: визуальные проверки — пустая мини-карточка ФЛ; полная карточка
  (Параметры, Покупки, Активности); заполненная карточка; визитка из договора
  займа Сизова. Перед снимком фиксируется режим «Колонки», чтобы эталон
  не зависел от порядка тестов.
- `test-2`: визуальные проверки 11 разделов карточки темы «Продажа товаров
  и услуг»; эталоны пересняты под тему test.
- `test-3`: доступность страницы входа Saby.
- `test-4`: функциональные проверки карточки ФЛ — структура мини-карточки,
  закрытие без сохранения, последовательное переключение вкладок, данные
  заполненного клиента и визитка из договора займа.
- `test-5`: функциональные проверки темы — полнота меню, содержимое воронки
  (этапы «Новый», «Знакомство», «Коммерческое предложение», «Оплата»,
  «Отгрузка», «Товар доставлен», «Сделка не состоялась» и итоги на стенде test),
  параметры, роли, ссылки верхней навигации и последовательный обход разделов.
- `test-6`: открытие карточки ФЛ по ссылке, скопированной из живой карточки
  Сизова или Горохова, в новой вкладке; отдельно проверяется команда
  «В новой вкладке». Кнопка копирования ссылки («Ссылка/Поделиться», на test —
  «Скопировать в буфер») копирует ссылку сразу, а команда «В новой вкладке»
  находится в подменю этой кнопки в меню карточки. Ссылка читается из буфера
  обмена, а не задаётся в тесте.
- `test-7`: реестр «Контактные лица» — активный раздел, список контактов
  «Сизов Виктор Генадьевич», «Горохов Евгений Олегович» и «Большие Данные
  Физик», телефон в строке Сизова, поиск по фамилии, фильтры по полу и возрасту.
- `test-8`: реестр «Темы» — активный раздел, группа «Продажи», темы
  «Продажа товаров и услуг» и «Проверка СПК», переход в карточку темы.
  Окна счётчиков «В работе» и «Новый, Новые» проверяются; «Просроченные»
  пропущен: Saby не разрешает срок сделки раньше текущей даты.
- `test-9`: два сценария с временной ФЛ — заполнение мини-карточки (ФИО, телефон,
  примечание, дата рождения, пол, адрес, паспорт, место рождения) с проверкой
  в полной карточке и изменением примечания; создание ФЛ с переходом в полную
  карточку, заполнением основных полей, сохранением и повторным открытием.
- `test-10`: создание временной темы «Продажи», проверка этапа «Новый», открытие
  карточки этапа, изменение его названия, сохранение темы, повторное открытие
  и удаление. Реестр открывается по `SABY_THEME_UUID` стенда test
  (`5440011c-8d41-11e7-adf1-005056b7473e`).
- `test-11`: пустой тестовый профиль — скриншот заглушки и проверка её
  положения; создание и удаление по отдельности физического лица, контактного
  лица (с временной организацией), папки, тега и выборки с фильтром
  «Пол» = «Мужской». Каждый тест завершается проверкой, что страница снова
  показывает исходную заглушку.
- `test-12`: документы продаж в карточке ФЛ — создание «Счёта», «Заказа от
  покупателя», «Реализации» и «Коммерческого предложения», сохранение
  комментария, отображение в списке и фильтре, фильтрация по типу, поиск по
  комментарию, редактирование сохранённого документа и удаление счёта с
  проверкой исчезновения его типа из фильтра.
- `test-13`: копирование темы «Проверка СПК» — код этапа «Код при копировании»,
  итог «Итоги пользователя», формула видимости перехода, формы, параметры и
  доп. поля копии; изменение кода формулы в копии с проверкой неизменности
  оригинала и уникального UUID; валидация пустого, пробельного и дублирующего
  имени; две копии с разными UUID; проверка итога «Отрицательно»; перенос
  инструкции этапа и вложений. Тема «Проверка СПК» подготовлена на test.
- `test-14`: новая карточка ФЛ под фичей `crm_new_individual` — данные
  демо-клиента «Сизов Виктор Генадьевич» (на fix использовалась «Проверка
  Карточки Физика», на test её нет) в режимах «В строку», «Справа» и «Колонки»;
  автоматическое переключение при изменении ширины; запоминание режима после
  закрытия и открытия; список режимов и маркер активного режима в окне
  «Навигация»; построение каждой вкладки в каждом режиме и после смены режима;
  все вкладки пустой карточки; стабильная ширина при переключении вкладок после
  открытия по ссылке; максимальная ширина с переходом в «Колонки» (viewport
  1600px); минимальная ширина 600px. Плашка периода в продажах пропущена:
  каталог товаров test пуст, продажу с суммой создать нельзя. Пустая
  карточка создаётся и удаляется в тесте.
- `test-15`: карточка темы из реестра сделок — пустая карточка создания темы
  через (+) в Канбане (пустое название, этап «Новый», пустая воронка, разделы);
  заполненная карточка темы «Продажа товаров и услуг» из доски темы через
  «Редактировать тему» (название, этапы «Новый», «Знакомство», «Отгрузка»
  и итоги); каждая из 11 вкладок заполненной карточки проверяется отдельным
  тестом. Компактная мини-карточка темы в шапке сделки на test пропущена:
  в теме нет сделок. Все проверки только открывают карточки и закрывают их
  без сохранения.
- `test-16`: карточка темы «Продажа товаров и услуг» по ссылке в отдельном
  окне — ссылка копируется из живой карточки темы в реестре сделок и
  открывается в новой вкладке; проверяются название, кнопка «Изменить», все
  11 разделов и каждая вкладка отдельным тестом.
  Карточка открывается в режиме просмотра, данные не изменяются.

Сценарии `test-1` — `test-8`, `test-15` и `test-16` только читают данные.
`test-9` — `test-14` (кроме пропущенного на test `test-13`) создают временные
записи с уникальными именами и удаляют их после проверки; `afterEach` удаляет
запись и при падении теста, чтобы не засорять общий стенд. Матрица покрытия
и список непокрытых областей — в `COVERAGE.md`.
